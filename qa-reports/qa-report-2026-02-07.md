## Executive Summary

The 002-local-data-ingestion branch introduces significant new functionality (CatalogSidebar, ImportDialog, IngestionProgress, file watching) but has two critical build configuration issues that prevent the app from launching. A `node:os` module externalization bug in the worker build causes the DuckDB worker to crash on startup, rendering the app non-functional. Additionally, a race condition in the query data subscription path could cause result loss for fast queries. After fixing the build issue, unit tests pass (682/682) and typecheck is clean. Live UI testing was blocked by the build issues; a code-level audit was performed instead.

## Issue Details

### QA-012: Worker build missing `node:os` external — app crashes on launch

- **Severity**: P0
- **Area**: Build System / Worker
- **Status**: FIXED in this session
- **Reproduction Steps**:
  1. Run `npx electron-forge start` to build and launch
  2. Observe the worker log: `Module "node:os" has been externalized for browser compatibility. Cannot access "node:os.totalmem" in client code.`
  3. App launches but worker thread crashes immediately
  4. Startup sequence hangs at `workerManager.spawn()` — no BrowserWindow is created
  5. App appears to hang (Electron process running, no window)
- **Expected Behavior**: Worker thread starts normally, app creates a window
- **Actual Behavior**: Worker crashes with Vite browser-externalization error for `node:os`. The DuckDB connection module (`src/workers/duckdb-connection.ts:1`) imports `os` from `node:os` to compute memory limits via `os.totalmem()`. Vite's library-mode build treats `node:` imports as browser-externalizable unless explicitly listed in `rollupOptions.external`.
- **Console Output**: `Worker error: Module "node:os" has been externalized for browser compatibility. Cannot access "node:os.totalmem" in client code.`
- **Fix Applied**: Added `/^node:/` regex to `rollupOptions.external` in the worker build config in `vite.main.config.ts` (line 30). This externalizes all `node:*` imports so they resolve at runtime via Node.js `require()`.
- **Affected Files**: [vite.main.config.ts](vite.main.config.ts) (lines 26-30), [src/workers/duckdb-connection.ts](src/workers/duckdb-connection.ts) (line 1)

### QA-013: Race condition in QueryEditor data subscription — early batches lost

- **Severity**: P0
- **Area**: Query Editor / Data Plane
- **Status**: New
- **Reproduction Steps**:
  1. Open the app and create a new Query tab
  2. Type a very fast query: `SELECT 1 AS test`
  3. Press Execute (or Cmd+Enter)
  4. `handleExecute` calls `window.datspace.query.execute(sql)` and receives `result.queryId`
  5. `setQueryId(result.queryId)` triggers a state update
  6. The `useEffect` at [QueryEditor.tsx:76](src/renderer/components/QueryEditor.tsx#L76) depends on `[queryId, isExecuting, activeTab?.id]` — it subscribes to `onData` only after the state update propagates (next render cycle)
  7. If Arrow batches arrive between the IPC response and the `onData` subscription, they are lost
- **Expected Behavior**: All Arrow batches from the query are received and displayed
- **Actual Behavior**: For fast queries (cached results, simple expressions), the first batch(es) may arrive before the `onData` listener is registered, causing them to be silently dropped. The result grid may show incomplete or no data.
- **Suggested Fix**: Subscribe to `onData` **before** calling `execute()`. Use a ref to store the expected queryId, and set up the subscription eagerly. Alternatively, have the preload bridge buffer early batches until a subscriber registers for a given queryId.
- **Affected Files**: [src/renderer/components/QueryEditor.tsx](src/renderer/components/QueryEditor.tsx) (lines 76-112, 114-148)

### QA-014: Ingestion event listeners update non-existent Dexie records

- **Severity**: P1
- **Area**: App.tsx / Ingestion
- **Status**: New
- **Reproduction Steps**:
  1. Import a file via drag-and-drop or file picker
  2. The Main process emits `INGESTION_PROGRESS` events via push
  3. [App.tsx:136](src/renderer/App.tsx#L136) calls `db.ingestion_jobs.where('id').equals(event.jobId).modify(...)`
  4. If the renderer hasn't yet received the `ImportFilesResponse` and created the Dexie record, `modify()` silently updates zero records
  5. Progress updates are lost; UI shows stale state
- **Expected Behavior**: Progress updates should always be reflected in the UI
- **Actual Behavior**: Early progress events are silently discarded if the ingestion job record doesn't exist yet in Dexie
- **Suggested Fix**: Use `db.ingestion_jobs.put()` (upsert) instead of `modify()`, or ensure the Main process creates the job record synchronously before emitting any progress events.
- **Affected Files**: [src/renderer/App.tsx](src/renderer/App.tsx) (lines 136-170)
